# خطة تنفيذ إضافة alborsa-platform

> الحالة: خطة مقترحة. المدد تقديرات أولية وليست التزاماً، وتُعاد معايرتها بعد حسم مزود البيانات ومراجعة عينات المحتوى والوسطاء.

## 1. تعريف الـMVP التقني

الإضافة الأولى تدعم:

- المحتوى العربي وروابطه بالأصول.
- سجل الأصول وصفحات تجريبية لعدد محدود من الأسهم والأصول.
- مصدر بيانات واحد قابل للاستبدال، مع Mock Provider للتطوير.
- ملفات الوسطاء والتقييم التحريري.
- مراجعات المستخدمين الخاضعة للمراجعة.
- مقارنة حتى 3 وسطاء.
- إدارة روابط الأفلييت وتتبع الضغطات.
- ست أدوات مالية بدون حساب مستخدم.
- تكامل Yoast SEO وPolylang بدون إنشاء التصميم.

## 2. ترتيب التنفيذ

### المرحلة 0 — القرارات وإثبات البيانات

المدة التقديرية: 3–5 أيام عمل بعد توفر الردود الخارجية.

المهام:

- اعتماد حدود الـMVP.
- تحديد مصدر بيانات تداول ونوع الترخيص والتأخير.
- عمل Proof of Concept لاستجابة حقيقية من المزود.
- اعتماد سياسة مراجعات المستخدمين والتحقق.
- اعتماد سياسة الأفلييت والاحتفاظ ببيانات الضغطات.
- اعتماد بنية الروابط قبل تسجيل Post Types.
- عمل Audit لإعدادات Polylang وYoast وBreeze وObject Cache Pro وWP 2FA وWPS Hide Login، وليس حالة التفعيل فقط.
- تحديد سياسة تحديث للإضافات؛ لقطة 2026-09-15 تظهر أن التحديثات التلقائية معطلة للجميع.

معيار الخروج:

- لدينا عينة بيانات موثقة، قائمة حقول نهائية، وسياسة عرض للمصدر والتأخير.
- لا توجد تسمية «لحظي» غير مدعومة تعاقدياً.
- إعدادات الإضافات المؤثرة مصدرة أو موثقة، وتم تحديد الفروق المطلوبة بين Staging وProduction.

### المرحلة 1 — تأسيس الإضافة

المدة التقديرية: أسبوع.

حالة التنفيذ في 2026-09-16: نُفذ Scaffold وBootstrap وModule Registry ونظام migrations حتى الإصدار `4` وصلاحيات الإدارة والمحتوى وجدولا العلاقات وأحدث الأسعار وفحوص Soft dependencies وSite Health وWP-CLI وبوابات الجودة. لم يُشغّل بعد Smoke test على تثبيت WordPress حي، لذلك يظل معيار الخروج الخاص ببيئة WordPress النظيفة بحاجة تحقق تشغيلي.

المهام:

- إنشاء Plugin bootstrap وComposer autoloading.
- Module Registry وFeature flags.
- Activation/deactivation بدون Side effects خطرة.
- نظام Migrations بإصدار واضح.
- تعريف Capabilities.
- إعداد PHPCS، PHPStan، PHPUnit وCI.
- إضافة WP-CLI health command.
- إضافة فحوص Soft dependencies للإضافات الحالية مع Admin notices واضحة وبدون Fatal errors.

ملاحظات التنفيذ:

- في Foundation الأصلية (الإصدار 1) لم تنشأ migration أي جدول؛ يضيف الإصدار 2 جدول العلاقات، ويضيف الإصدار 3 صلاحيات محتوى الأنواع المنفذة. مسارات REST لا تعتمد على Migration جديدة.
- التعطيل يحذف قفل migration المؤقت فقط؛ لا يحذف version option أو capability أو بيانات مستقبلية.
- `manage_alborsa_platform` ممنوحة لـ`administrator` فقط. الإصدار 3 يمنح مجموعة قدرات `alb_content` لدوري `administrator` و`editor` بدون إنشاء دور منتج جديد أو Workflow نشر جديد.
- فحوص التبعيات تثبت Availability فقط، ولا تستبدل Audit الإصدارات والتراخيص والإعدادات والصحة.

معيار الخروج:

- الإضافة تعمل على تثبيت WordPress نظيف.
- التفعيل المتكرر لا يكرر بيانات ولا يكسر الجداول.
- اختبارات وبوابات الجودة تعمل تلقائياً.

### المرحلة 2 — المحتوى والأصول

المدة التقديرية: 1–1.5 أسبوع.

حالة التنفيذ: نُفذ جدول العلاقات و`RelationshipRepository` و`ContentAssetRelationshipService` المتحقق من أدوار كائنات المحتوى والأصل، ثم سُجلت `alb_analysis` و`alb_guide` و`alb_asset` والتصنيفات الستة الأساسية وحقول الهوية الثابتة للأصل وخريطة المزودين المحمية. مسارا تداول والفوركس يفرضان تصنيف الأصل في الاستعلام لمنع المسارات المكررة. يضبط `wpml-config.xml` ترجمة الكيانات والنسخ الانتقائي لحقول الأصل. نُفذ REST العام لقراءة الأصول، ومستورد CSV بواجهة WP-CLI وDry-run وتقارير أخطاء ومنع تكرار الهوية. لا تزال الحقول التحريرية المتبقية غير منفذة.

المهام:

- بناء جدول العلاقات وطبقة Repository وخدمة علاقات المحتوى بالأصول (منفذة لعلاقتي `mentions` و`analyzes`)؛ تبقى واجهة الإدارة ومسارات الكتابة قيد الانتظار.
- تسجيل Post Types وTaxonomies وفق القرار D-002 المعتمد (`alb_analysis` و`alb_guide` و`alb_asset` والتصنيفات الستة الأساسية منفذة).
- تسجيل الحقول والتحقق منها (حقول الأصل الثابتة وخريطة المزودين منفذة؛ الحقول التحريرية المتبقية قيد الانتظار).
- REST endpoints لقراءة الأصول (منفذة للقائمة والتفاصيل؛ مسارات المحتوى المنفصلة غير مطلوبة حالياً).
- CSV importer للأصول مع Dry-run وتقارير أخطاء (منفذ عبر `wp alborsa assets import`).
- تسجيل Post Types وTaxonomies في Polylang وإعداد `wpml-config.xml` للنسخ الانتقائي للحقول (منفذ للكيانات وحقول الأصل الحالية؛ التحقق الحي على Staging باقٍ).
- صلاحيات المحرر والمراجع (منفذة حالياً عبر دور WordPress `editor` وقدرات `alb_content` المشتركة؛ حالات Workflow مخصصة غير منفذة).

معيار الخروج:

- يمكن إنشاء أصل وربطه بخبر أو تحليل.
- يمكن استيراد مجموعة أصول بدون إنشاء تكرارات.
- لا تظهر الحقول الإدارية أو الحساسة في REST العام.

### المرحلة 3 — بيانات السوق

المدة التقديرية: 1–2 أسبوع حسب المزود.

حالة التنفيذ: نُفذ `QuoteProviderInterface` و`NormalizedQuote` و`MockQuoteProvider` بدون اتصالات خارجية، كما نُفذ جدول أحدث الأسعار و`QuoteRepository`. اختيار وبناء Adapter حقيقي ينتظر اعتماد D-001، والمزامنة والكاش وREST قيد التنفيذ.

المهام:

- `QuoteProviderInterface` وDTOs (منفذة).
- Mock Provider وFixtures للاختبار (منفذ كمزود حتمي يقبل Fixtures مطبعة).
- Adapter المزود الحقيقي.
- Normalization للعملات والتوقيت والأرقام.
- جدول أحدث الأسعار وRepository (منفذان عبر Schema الإصدار `4`).
- Scheduled sync وWP-CLI commands.
- Retry/backoff وstale fallback.
- Site Health panel لحالة المصدر.
- REST endpoint للسعر مع Cache headers.
- تكامل Object Cache Pro باستخدام WordPress Object Cache API بدون Full Flush.
- اختبار Breeze/Varnish وتوثيق استثناءات المسارات الديناميكية.

معيار الخروج:

- فشل المزود لا يعطل صفحات WordPress.
- كل قيمة تعرض معها `source` و`as_of` و`delay/status`.
- لا توجد External API calls في Frontend request lifecycle.

### المرحلة 4 — الوسطاء والمراجعات والأفلييت

المدة التقديرية: 1.5–2 أسبوع.

المهام:

- نموذج الوسيط والتراخيص والتقييمات.
- حساب النتيجة التحريرية من المحاور.
- خدمة المقارنة حتى 3 وسطاء.
- نموذج مراجعة مستخدم آمن ومعدل الطلبات.
- Workflow التحقق والمراجعة.
- جداول روابط الأفلييت والضغطات.
- Redirect handler مع Allowlist ومنع Open Redirect.
- Events للتكامل مع Analytics.

معيار الخروج:

- لا يمكن نشر شارة ترخيص بلا سجل ومصدر وتاريخ تحقق.
- التقييم التحريري منفصل بصرياً وبيانياً عن تقييم المستخدمين.
- تغيير رابط العرض يتم مرة واحدة ولا يحتاج تعديل المحتوى القديم.

### المرحلة 5 — الأدوات المالية

المدة التقديرية: 1–1.5 أسبوع.

المهام:

- Tool Registry.
- معادلات الأدوات الست.
- قواعد التقريب والتحقق ورسائل الأخطاء.
- Dynamic Block أو Render API لكل أداة بدون تصميم نهائي.
- Unit tests لحالات طبيعية وحدود وقيم غير صالحة.
- محول العملات يستخدم Quote Service ولا يتصل مباشرة بالمزود.

معيار الخروج:

- كل معادلة موثقة بافتراضاتها ومغطاة باختبارات.
- لا تحفظ مدخلات الزائر.
- يمكن للقالب استبدال HTML الخارجي بدون تغيير منطق الحساب.

### المرحلة 6 — SEO واللغات والتحرير والتشغيل

المدة التقديرية: أسبوع.

المهام:

- تكامل Yoast SEO وإضافة الكيانات المطلوبة إلى Schema graph الخاص به.
- Canonical وnoindex rules للصفحات الديناميكية.
- Schema graph بدون ازدواج.
- اختبار Polylang مع Post Types وTaxonomies وحقول Copy/Translate.
- حقول المصادر والكاتب والمراجع وآخر مراجعة.
- RSS importer إلى Draft مع منع التكرار.
- Audit log محدود للإجراءات الحساسة.
- Privacy exporter/eraser لمراجعات المستخدمين.

معيار الخروج:

- لا يوجد أكثر من مصدر يطبع نفس Schema entity.
- المحتوى المستورد لا يُنشر بدون مراجعة بشرية.
- صفحات الأصول الضعيفة يمكن إبقاؤها Draft أو Noindex.

### المرحلة 7 — التثبيت والتكامل مع القالب

المدة التقديرية: 3–5 أيام.

حالة الواجهة في 2026-09-16: نُفذ قالب مخصص أولي قابل للتعديل مع الصفحة الرئيسية وقوالب الأقسام والمحتوى. ما زالت عقود البيانات الديناميكية وSeed content والفحص الحي على Staging ضمن هذه المرحلة.

المهام:

- Integration tests للصلاحيات وREST والجداول.
- Performance profiling للـqueries والـcron.
- Security review للنماذج والتحويلات والمدخلات.
- توثيق API المتاح للمصمم/مطور القالب.
- Seed content وFixtures تساعد في تصميم جميع الحالات.

معيار الخروج:

- يستطيع المصمم/مطور القالب رؤية حالات: ارتفاع، انخفاض، بيانات قديمة، بيانات غير متاحة، وسيط بلا عرض، ومراجعة غير موثقة.
- لا يحتاج القالب إلى قراءة Post Meta عشوائياً أو معرفة تفاصيل المزود.

## 5. Definition of Done لكل Feature

أي ميزة لا تعتبر مكتملة إلا عند تحقق الآتي:

- صلاحيات الوصول محددة ومختبرة.
- المدخلات محققة ومطهرة والمخرجات escaped.
- Unit أو Integration tests للحالات الأساسية والفشل.
- لا يوجد اتصال خارجي في تحميل الصفحة إلا Embed مصرح به.
- حالة التعطل والبيانات الفارغة معرفة.
- النصوص قابلة للترجمة وRTL لا يعتمد عليه المنطق.
- البيانات العامة موثقة لمطور القالب.
- الأثر على الخصوصية والـSEO موضح.
- تم اختبار الميزة مع الإضافات النشطة التي تمس نفس المسار.
- Migration وRollback التشغيلي موثقان إن وُجد تعديل بيانات.

## 6. عقد التكامل مع القالب

بدأ تنفيذ التصميم المعتمد قبل اكتمال بقية وحدات المنتج، لذلك تعمل القائمة التالية كعقد تكامل يجب إكماله قبل ربط الحالات الديناميكية النهائية:

- قائمة Templates المطلوبة وحالاتها.
- بيانات تجريبية واقعية ومنزوعة الأسرار.
- API contract للبيانات الديناميكية.
- Block inventory ووظيفة كل Block.
- Class/attribute contract للـHTML الدلالي.
- أمثلة لحالات Loading، Empty، Error وStale.
- حدود النصوص والأرقام اللازمة لكل مكون.

القالب الحالي لا يخترع العقود الناقصة: يعرض حالات فارغة أو غير متاحة إلى أن تقدم الإضافة البيانات والخدمات الموثقة.
