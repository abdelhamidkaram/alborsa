# سجل تقدم التنفيذ — alborsa-platform

> هذا الملف هو سجل تتبع للخطوات المنفذة وطابور المهام المفوضة القادمة. يوضح ما نُفذ فعلياً ويفصله بدقة عما هو مقترح أو قيد الانتظار، مع توضيح حدود التحقق التشغيلي.

## 1. ملخص الحالة العامة

- **التاريخ**: 2026-09-16
- **إصدار قاعدة البيانات المنفذ**: `4` (`alborsa_platform_db_version`)
- **الوحدات المسجلة**: `FoundationModule` و`EditorialModule` و`AssetsModule` و`MarketDataModule` و`BrokersModule` و`FinancialToolsModule` و`SeoIntegrationModule`
- **حالة القرارات الحرجة**: القرار `D-002` معتمد؛ العربية على `/` من دون بادئة، والإنجليزية تحت `/en/`. سُجلت أنواع التحليل والدليل والأصل وتصنيفاتها الأساسية ومسارا REST لقراءة الأصول.
- **حالة القالب**: القالب المخصص `alborsa` منفذ كنسخة RTL متجاوبة ومربوط بعقود الأسعار والحاسبات والوسطاء والتحرير العامة؛ الفحص الحي وإدخال المحتوى وضبط WordPress على Staging لم ينفذ بعد.

## 2. سجل الخطوات المنفذة

### خطوة 1: تأسيس طبقة Foundation (المرحلة 1)
- **الحالة**: مكتملة
- **المنفذ فعلياً**:
  - Plugin bootstrap مع Composer PSR-4 autoloading.
  - `ModuleRegistry` وواجهة `Module`.
  - وحدة `FoundationModule`.
  - `MigrationRunner` بإصدار Schema رقم `1` يهيئ صلاحية `manage_alborsa_platform` لدور `administrator`.
  - دورة تفعيل وتعطيل آمنة تدعم Multisite مع قفل ترحيل مؤقت (`alborsa_platform_migration_lock`).
  - فحوص Soft dependencies للإضافات السبع بدون Fatal errors عند غيابها.
  - فحصان داخل WordPress Site Health وأمر WP-CLI: `wp alborsa health`.
  - بوابات الجودة: PHPCS، PHPStan (Level 7)، واختبارات وحدة PHPUnit مع Brain Monkey.

### خطوة 2: ترحيل قاعدة بيانات جدول العلاقات (المرحلة 2 — الخطوة الأولى المحدودة)
- **الحالة**: مكتملة
- **المنفذ فعلياً**:
  - ترقية إصدار الـSchema من `1` إلى `2` في `MigrationRunner::LATEST_VERSION`.
  - إنشاء جدول العلاقات `{$wpdb->prefix}alb_relationships` بشكل idempotent باستخدام WordPress `dbDelta`.
  - الأعمدة المنفذة وفق وثيقة `docs/02-data-model.md`:
    - `id bigint(20) unsigned NOT NULL auto_increment`
    - `from_object_id bigint(20) unsigned NOT NULL`
    - `from_object_type varchar(32) NOT NULL`
    - `to_object_id bigint(20) unsigned NOT NULL`
    - `to_object_type varchar(32) NOT NULL`
    - `relation_type varchar(32) NOT NULL`
    - `sort_order int(11) NOT NULL default 0`
    - `created_at datetime NOT NULL` (حقل `datetime`؛ فرض توقيت UTC هو مسؤولية خدمة العلاقات عند الإدخال مستقبلاً)
  - المفاتيح والفهارس:
    - `PRIMARY KEY  (id)`
    - `UNIQUE KEY uq_relationship (from_object_id, from_object_type, to_object_id, to_object_type, relation_type)`
    - `KEY ix_target_lookup (to_object_id, to_object_type, relation_type)`
  - القيود المعمارية الملتزم بها:
    - عدم إضافة Foreign Keys نظراً لتعدد الكيانات المشار إليها عبر الأنواع المختلفة.
    - استخدام بادئة الجدول الحالية `{$wpdb->prefix}alb_relationships` (مثال لموقع مفرد: `wp_alb_relationships`) مع الاعتماد على دورة `Activation` الحالية لدعم Multisite.
    - حفظ الإصدار في قاعدة البيانات فقط بعد التحقق من وجود الجدول، مع إرجاع `WP_Error` وعدم رفع الإصدار عند الفشل.
    - الحفاظ التام على تكرارية تشغيل Migration الإصدار الأول والثاني بأمان (Idempotency).
  - الاختبارات:
    - 5 اختبارات PHPUnit معزولة وموجهة في `MigrationRunnerTest` تفحص صحة استعلام SQL، وترقية الإصدارين 1 و2 معاً، والترقية المباشرة من 1 إلى 2، وفشل إنشاء الجدول، وغياب اتصال قاعدة البيانات.
- **حدود التحقق التشغيلي**:
  - **بوابة الجودة الشاملة (`composer quality`)**: تم تشغيلها والتحقق منها بنجاح من قِبل الـOrchestrator المستقل بنتيجة نظيفة بالكامل:
    - **فحص بناء الجملة (PHP Lint)**: فحص 27 من 27 ملفاً بنجاح دون أي خطأ (27 PHP files linted).
    - **معايير ووردبريس القياسية (PHPCS)**: اجتياز كامل بدون أي أخطاء أو تحذيرات (PHPCS clean).
    - **التحليل الساكن المتقدم (PHPStan)**: المستوى السابع دون أخطاء (PHPStan Level 7, 0 errors).
    - **اختبارات الوحدة (PHPUnit)**: اجتياز كامل بنتيجة **17 tests, 56 assertions** دون أي إخفاق.
  - **حدود التحقق التكاملي والبيئة الحية**: التنفيذ الفعلي لـ`dbDelta` داخل قاعدة بيانات MySQL/MariaDB حية وتفعيل الشبكة عبر عدة مواقع (Multisite) يظلان حداً للتحقق التكاملي في بيئة ووردبريس حية.

### خطوة 3: أنواع المحتوى التحريرية الأساسية
- **الحالة**: مكتملة
- **المنفذ فعلياً**:
  - تسجيل `alb_analysis` و`alb_guide` كنوعي محتوى عامين يدعمان REST القياسي والمراجعات.
  - اعتماد rewrite bases: `/tahleel/` للتحليل و`/taleem/` للدليل، بدون الاعتماد على القالب.
  - إضافة خدمة Foundation ذات إصدار لمسح rewrite rules مرة واحدة بعد اكتمال تسجيل الوحدات، مع Soft Flush فقط.
  - تغطية التسجيل ودورة rewrite rules والتفعيل المفرد والشبكي باختبارات وحدة معزولة.

### خطوة 4: سجل الأصول والتصنيفات الأساسية
- **الحالة**: مكتملة
- **المنفذ فعلياً**:
  - تسجيل `alb_asset` ودعمه في محرر المكونات وREST القياسي والمراجعات، بدون أرشيف عام افتراضي.
  - تسجيل `alb_topic` و`alb_guide_level` و`alb_guide_track` و`alb_asset_type` و`alb_exchange` و`alb_sector`.
  - إبقاء أرشيفات التصنيفات وRewrite rules الخاصة بها مغلقة حتى اعتماد عقود روابطها.
  - تنفيذ `/aswaq/tadawul/{symbol}/` للأصل المصنف `stock` و`tadawul`، و`/forex/{pair}/` للأصل المصنف `forex`.
  - فرض Tax Query لكل مسار حتى لا يظهر الأصل نفسه على مسارات تصنيف غير صحيحة.
  - بوابات الجودة: 38 اختباراً و206 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**: تسجيل الكيانات ومساراتها مغطى باختبارات معزولة؛ يلزم Smoke test على WordPress حي مع Polylang وYoast قبل الإطلاق.

### خطوة 5: حقول الأصول وسياسة Polylang
- **الحالة**: مكتملة لحقول الأصل الحالية
- **المنفذ فعلياً**:
  - تسجيل ستة حقول عامة للرمز والعملات وISIN والموقع الرسمي وحالة الإدراج، مع Normalization وSanitization وصلاحية `edit_post`.
  - تسجيل `_alb_provider_mappings` كحقل Array محمي، مع تطبيع كل Record ومنع ظهوره في REST القياسي.
  - إضافة `custom-fields` إلى دعم `alb_asset` حتى تعمل الحقول العامة المسجلة مع REST القياسي.
  - إضافة `wpml-config.xml` صالح XML يترجم الأنواع والتصنيفات المنفذة ويزامن حقول الأصل المحايدة باستخدام `copy`.
  - بوابات الجودة: 50 اختباراً و261 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء، ونجاح `xmllint`.
- **حدود التحقق التشغيلي**: تحميل `wpml-config.xml` والمزامنة الفعلية بين العربية والإنجليزية يحتاجان اختبار Polylang على Staging.

### خطوة 6: صلاحيات المحتوى
- **الحالة**: مكتملة للأنواع الحالية
- **المنفذ فعلياً**:
  - نقل `alb_analysis` و`alb_guide` و`alb_asset` من قدرات `post` العامة إلى خريطة `alb_content`/`alb_contents` مع `map_meta_cap`.
  - إضافة Migration الإصدار `3` لتثبيت عشر قدرات Primitive للتحرير والنشر وقراءة المحتوى الخاص والحذف.
  - منح قدرات المحتوى إلى `administrator` و`editor` فقط، مع بقاء `manage_alborsa_platform` لدى المدير فقط.
  - عدم إنشاء دور أو Post Status جديد قبل اعتماد Workflow تحريري تفصيلي.
  - بوابات الجودة: 54 اختباراً و281 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**: ترقية الأدوار وتطبيق `map_meta_cap` يحتاجان Integration test على WordPress حي.

### خطوة 7: خدمة علاقات المحتوى بالأصول
- **الحالة**: مكتملة كخدمة داخلية
- **المنفذ فعلياً**:
  - إضافة `ContentAssetRelationshipService` فوق `RelationshipRepository`.
  - قبول كائنات `WP_Post` موجبة الهوية فقط، مع مصادر `post` و`alb_analysis` و`alb_guide` وهدف `alb_asset`.
  - دعم `mentions` و`analyzes` للربط والحذف والقراءة من جهة المحتوى أو الأصل.
  - رفض أنواع الكائنات والعلاقات غير المدعومة قبل أي كتابة في الجدول.
  - بوابات الجودة: 64 اختباراً و305 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**: الخدمة بلا Admin UI أو REST write route، وسلوك الجدول الفعلي ما زال يحتاج Integration test على MySQL/WordPress حي.

### خطوة 8: REST العام لقراءة الأصول
- **الحالة**: مكتملة لعقد القائمة والتفاصيل
- **المنفذ فعلياً**:
  - إضافة `GET /wp-json/alborsa/v1/assets` للأصول المنشورة مع `page` و`per_page` و`search` و`asset_type` و`exchange`.
  - حد أقصى 100 عنصر للصفحة ورقم صفحة أقصى 1000، مع تفعيل Meta وTerm caches ومنع استعلامات العد غير المطلوبة.
  - إضافة `GET /wp-json/alborsa/v1/assets/{id}` للتفاصيل والمحتوى المنشور المرتبط بعلاقتي `mentions` و`analyzes`.
  - حجب `_alb_provider_mappings` وأخطاء قاعدة البيانات الداخلية، وإرجاع أخطاء عامة آمنة عند تعذر التصنيفات أو العلاقات.
  - تجميع تحميل المحتوى المرتبط في استعلام واحد، وحد قراءات Repository إلى 100 علاقة.
  - بوابات الجودة: 71 اختباراً و342 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**: تسجيل المسارات واستجابة Polylang وYoast والكاش تحتاج Smoke test على WordPress حي؛ الاختبارات الحالية معزولة عن WordPress وقاعدة البيانات.

### خطوة 9: مستورد الأصول CSV
- **الحالة**: مكتملة عبر WP-CLI
- **المنفذ فعلياً**:
  - إضافة `wp alborsa assets import <file> [--dry-run]` مع تقرير لكل صف وملخص للإضافة والتحديث والفشل.
  - فرض حد 5MB و5000 صف، والتحقق الصارم من Header وعدد الأعمدة والقيم قبل الكتابة.
  - جعل `language` و`title` و`canonical_symbol` و`asset_type` أعمدة إلزامية، مع لغة Polylang صريحة وTerms موجودة ومطابقة للغة.
  - منع التكرار بهوية `(language, canonical_symbol)` داخل الملف وعبر الأصول الموجودة، ورفض الحالات القائمة الملتبسة.
  - إنشاء الأصول الجديدة كـ`draft` افتراضياً، ومنع نشر الإنجليزية في المرحلة الحالية.
  - الحفاظ على القيم الاختيارية عند غياب أعمدتها في تحديث موجود، مع مرور الكتابة عبر `AssetUpsertService` بدلاً من جداول مباشرة.
  - بوابات الجودة: 83 اختباراً و369 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**: تشغيل الأمر ضد WordPress وPolylang حيَّين واستيراد عينة حقيقية يحتاجان Smoke test على Staging؛ الاختبارات الحالية معزولة.

### خطوة 10: عقد الأسعار المطبع وMock Provider
- **الحالة**: مكتملة للحد المحايد عن المزود
- **المنفذ فعلياً**:
  - إضافة `QuoteProviderInterface` لجلب دفعة رموز مزود وإرجاع قائمة مرتبة من Quotes أو خطأ دفعة معروف.
  - إضافة `NormalizedQuote` غير قابل للتغيير، مع هوية مزود، قيم سعرية اختيارية، عملة، توقيت سوق واستلام UTC، تأخير، حالة، و`payload_hash`.
  - إبقاء القيم العشرية كسلاسل مطبعة بحد 20 خانة صحيحة و10 عشرية، ورفض Floating-point inputs والصيغة العلمية.
  - قبول توقيت ISO-8601 ذي منطقة زمنية فقط وتحويله إلى `Y-m-d H:i:s` بتوقيت UTC.
  - إضافة `MockQuoteProvider` حتمي بحد 100 رمز بدون Network I/O أو مزود حقيقي.
  - بوابات الجودة: 94 اختباراً و396 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**: لا يوجد Adapter حقيقي أو ترخيص أو مستوى تأخير معتمد؛ يظل ذلك محجوباً بالقرار D-001.

### خطوة 11: جدول أحدث الأسعار وRepository
- **الحالة**: مكتملة لطبقة التخزين
- **المنفذ فعلياً**:
  - ترقية Schema إلى الإصدار `4` وإنشاء `{$wpdb->prefix}alb_market_quotes` عبر `dbDelta` مع تحقق وجود الجدول قبل حفظ الإصدار.
  - استخدام `decimal(30,10)` للقيم السعرية وSQL `NULL` للقيم غير المتاحة، مع عدم إضافة Foreign Keys أو Price history.
  - مفتاح فريد `(asset_id, provider_key)` وفهارس لهوية المزود ولمتابعة الحالة ووقت الاستلام.
  - إضافة `QuoteRepository` بعملية Prepared upsert تحافظ على Decimal strings وقراءة محدودة لصف أصل/مزود واحد.
  - تغطية فشل إنشاء الجدول وفشل القراءة والكتابة بدون رفع الإصدار أو إخفاء الخطأ عن الطبقة الداخلية.
  - بوابات الجودة: 103 اختبارات و436 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**: يلزم تشغيل Migration وupsert فعليين على MySQL/MariaDB في Staging.

### خطوة 12: القالب المخصص وواجهات العرض
- **الحالة**: مكتملة كنسخة أولى قابلة للتعديل
- **المنفذ فعلياً**:
  - اعتماد اتجاه Editorial Signal ونظام تصميم RTL موثق في `PRODUCT.md` و`DESIGN.md` و`.impeccable/design.json`.
  - إنشاء القالب المستقل `wp-content/themes/alborsa` بدون نقل منطق المنتج من `alborsa-platform`.
  - تنفيذ الترويسة والتنقل المتجاوب وشريط حالة السوق والتذييل وMobile dock والبحث.
  - تنفيذ الصفحة الرئيسية بموجز اليوم وآخر الأخبار وملخص الأسواق وحالة الأكثر تداولاً والتحليل والوسيط المميز والتعليم والنشرة.
  - تنفيذ صفحات الأسواق والأخبار والوسطاء والأدوات، وأرشيفي التحليل والتعليم، وصفحات المحتوى والأصول المفردة، والبحث و404.
  - استخدام المحتوى المنشور وحقول هوية الأصل العامة فقط، مع حالات صريحة لما يعتمد على مزود السوق أو منهجية الوسطاء أو مزود البريد أو خدمات الأدوات.
  - اجتياز PHP syntax وWordPress Coding Standards وفحص الأنماط الخاص بنظام التصميم للملفات الجديدة.
- **حدود التحقق التشغيلي**:
  - لا يحتوي المستودع على تثبيت WordPress كامل أو `wp-config.php`، لذلك لم ينفذ Visual QA حي أو اختبار إعداد القوائم والصفحات وPolylang وYoast والكاش.
  - لا يوجد مزود سعر حقيقي أو توصيات وسطاء؛ الواجهة تعرض حالة عدم التوفر أو آخر Snapshot المنشور فقط طبقاً لعقود الإضافة.

### خطوة 13: تشغيل وحدة بيانات السوق المحايدة
- **الحالة**: مكتملة برمجياً بدون Adapter حقيقي
- **المنفذ فعلياً**:
  - تسجيل `MarketDataModule` واكتشاف Adapters عبر Filter موثق باسم `alborsa_platform_quote_providers` بدون تفعيل `MockQuoteProvider` في الإنتاج.
  - قراءة `_alb_provider_mappings` المحمية للأصول المنشورة واختيار سجلات `quotes` المفعلة، مع المرور على كل الأصول في صفحات ثابتة من 100 أصل.
  - إضافة `QuoteSyncService` للتحقق من هوية الدفعة واكتمالها، وإزالة تكرار الرمز داخل الدفعة، وحفظ آخر Snapshot لكل ترجمة أصل.
  - إضافة `wp alborsa market sync --provider=<key>` ليعمل من Server Cron خارج طلبات الواجهة، بدون تسجيل WP-Cron يعتمد على الزيارات.
  - إضافة `QuoteCache` على WordPress Object Cache group مخصص ومفاتيح لكل أصل/مزود، بدون Full Flush أو Breeze purge.
  - حفظ حالة آخر نجاح وفشل للمزوّد بدون رسالة الخطأ الخام، واستخدامها لإرجاع آخر قيمة سليمة بوسم `stale` عند فشل أحدث.
  - إضافة `QuoteReadService` و`GET /wp-json/alborsa/v1/assets/{id}/quote` مع بيانات المصدر والوقت والتأخير والحالة وCache headers، وحجب هوية المزوّد الداخلية.
  - إضافة فحص Site Health يميز بين عدم وجود مزوّد، ومزامنة تحتاج انتباهاً، وحالة سليمة.
  - بوابات الجودة: 114 اختباراً و480 assertions، مع PHPCS نظيف وPHPStan Level 7 دون أخطاء.
- **حدود التحقق التشغيلي**:
  - D-001 ما زال مفتوحاً؛ لا يوجد Adapter أو ترخيص أو Server Cron فعلي، ولا يجوز وصف البيانات بأنها لحظية.
  - يلزم Smoke test على WordPress/MySQL حي، والتحقق من Object Cache Pro وBreeze/Varnish ومسار REST تحت حمل حقيقي.
